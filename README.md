# FPGA-Based Real-Time Background Subtraction Using OV7670 and DE2-115

## Overview

This project implements a **real-time video background subtraction system on FPGA** using an **OV7670 camera module**, **Terasic DE2-115 development board**, and **VGA monitor**.

The OV7670 camera provides a live RGB565 video stream. The FPGA captures the camera data, converts RGB565 pixels to RGB444, reduces the image resolution from 640×480 to 320×240, stores both live and reference-background frames, performs pixel-wise foreground detection, removes noise using a 3×3 majority filter, and displays the processed result on a VGA monitor.

The system supports:

- Normal live video
- Background subtraction
- Original-color foreground with black background
- Binary white foreground mask
- Adjustable foreground threshold
- VGA diagnostic color bars
- Camera/debug status LEDs

# Main Modules

## 1. `bg_subtraction_top.v`

This is the **top-level integration module**.

Responsibilities:

- Receives the 50 MHz DE2-115 clock
- Generates a 25 MHz VGA-side clock
- Instantiates all project modules
- Synchronizes push buttons and switches
- Controls OV7670 configuration
- Controls background capture
- Reads live and background pixels
- Calculates luminance and RGB differences
- Generates the foreground score
- Performs threshold comparison
- Selects live video, foreground output, binary mask, or VGA test pattern
- Controls debug LEDs
- Sends the final RGB pixel to the VGA interface

The actual background-subtraction decision is implemented in this module.

---

## 2. `ov7670_controller.v`

This module controls OV7670 initialization.

Responsibilities:

- Generates the camera XCLK
- Keeps the camera powered and out of reset
- Receives camera register commands from `ov7670_registers.v`
- Sends commands through `i2c_sender.v`
- Advances to the next camera register
- Indicates when configuration is complete

The camera XCLK is generated by dividing the 50 MHz input clock by two.

```text
50 MHz / 2 = 25 MHz
```

---

## 3. `ov7670_registers.v`

This module acts like an **internal ROM / lookup table** containing the OV7670 initialization sequence.

Each 16-bit command contains:

```text
[15:8] = OV7670 register address
[7:0]  = value written to the register
```

For example:

```text
16'h4010
```

means:

```text
Register address = 0x40
Register value   = 0x10
```

The register sequence configures:

- Camera reset
- RGB output mode
- RGB565 format
- Clock settings
- Automatic gain control
- Color conversion matrix
- Gamma processing
- Horizontal image window
- Vertical image window
- Mirror/flip configuration

The final working color matrix used in this project is:

```text
4F40
5034
510C
5217
5329
5440
581E
```

---

## 4. `i2c_sender.v`

This module performs SCCB/I²C-like communication with the OV7670 camera.

It sends:

```text
Camera Device Address
Register Address
Register Value
```

using:

```text
SIOC
SIOD
```

The OV7670 write ID used in the controller is:

```text
0x42
```

A simple way to understand the configuration chain is:

```text
ov7670_registers = WHAT to send
i2c_sender       = HOW to send it
ov7670_controller = WHEN to send it
```

---

## 5. `ov7670_capture_bg.v`

This module is responsible for camera pixel capture and background-frame capture.

Responsibilities:

- Samples camera data, HREF and VSYNC on the falling edge of PCLK
- Processes the captured values on the rising edge of PCLK
- Combines two 8-bit camera bytes into one RGB565 pixel
- Supports optional RGB565 byte swapping
- Converts RGB565 to RGB444
- Reduces resolution from 640×480 to 320×240
- Continuously writes the live frame buffer
- Captures one full background frame after KEY1 is pressed
- Generates background busy and background valid status signals

### PCLK Timing Method

Camera signals are sampled on the falling edge:

```text
Falling PCLK
→ sample CAM_D, HREF and VSYNC
```

Then processed on the rising edge:

```text
Rising PCLK
→ assemble and write the pixel
```

This provides approximately half a PCLK period for camera signals to settle and helped remove horizontal tearing in the video.

---

# RGB565 to RGB444 Conversion

The OV7670 produces RGB565:

```text
RRRRR GGGGGG BBBBB
```

This uses:

```text
Red   = 5 bits
Green = 6 bits
Blue  = 5 bits
Total = 16 bits
```

The project converts this to RGB444:

```text
RRRR GGGG BBBB
```

which uses:

```text
Red   = 4 bits
Green = 4 bits
Blue  = 4 bits
Total = 12 bits
```

The conversion used in the capture module is:

```verilog
wire [11:0] pixel444 = {
    pixel565[15:12],
    pixel565[10:7],
    pixel565[4:1]
};
```

### Why RGB444?

RGB444 is used because:

- It reduces frame-buffer memory usage
- It simplifies arithmetic
- Background subtraction does not require full RGB565 precision
- All three color channels have equal 4-bit widths

For one 320×240 frame:

```text
320 × 240 = 76,800 pixels
```

RGB565 memory:

```text
76,800 × 16 = 1,228,800 bits
```

RGB444 memory:

```text
76,800 × 12 = 921,600 bits
```

Therefore RGB444 saves approximately 25% of pixel-storage memory.

---

# Resolution Reduction

The incoming camera frame is:

```text
640 × 480
```

The FPGA stores and processes:

```text
320 × 240
```

This is called:

**2× spatial downsampling**

or

**VGA to QVGA resolution reduction**

The capture module keeps:

- Every second pixel horizontally
- Every second input line vertically

The relevant condition is:

```verilog
if (!x_pixel[0] && !y_line[0])
```

This means only even x and even y positions are stored.

Therefore:

```text
640 / 2 = 320
480 / 2 = 240
```

The number of pixels reduces from:

```text
640 × 480 = 307,200 pixels
```

to:

```text
320 × 240 = 76,800 pixels
```

This reduces the number of stored and processed pixels by a factor of four.

# Frame Buffers

Two RGB444 frame buffers are used.

## Live Frame Buffer

The live frame buffer is continuously updated with the newest camera frame.

It does not store every video frame permanently.

At every new frame:

```text
write address resets to 0
```

and the new frame overwrites the previous frame.

Therefore memory usage remains constant.

---

## Background Frame Buffer

The background frame buffer stores one fixed reference frame.

When `KEY1` is pressed:

```text
Background request
→ wait for next VSYNC
→ capture one complete frame
→ store it as background
```

The stored background remains unchanged until another background capture is requested.

---

# Frame Buffer Size

Resolution:

```text
320 × 240
```

Total locations:

```text
76,800
```

Each RGB444 pixel:

```text
12 bits
```

The frame-buffer address uses:

```text
17 bits
```

because:

```text
2^16 = 65,536  -> not enough

2^17 = 131,072 -> enough
```

# 320×240 to 640×480 Display

The stored video is 320×240 but the VGA display is 640×480.

The source coordinates are calculated using:

```verilog
wire [8:0] xs = h[9:1];
wire [7:0] ys = v[8:1];
```

This is equivalent to:

```text
source_x = VGA_x / 2
source_y = VGA_y / 2
```

Therefore each source pixel is displayed as a 2×2 VGA block.

---

# Frame Buffer Address Calculation

The RAM address is:

```text
address = y × 320 + x
```

Instead of using a multiplier:

```text
320 = 256 + 64
```

Therefore:

```text
y × 320
=
(y << 8) + (y << 6)
```

The code uses shift/concatenation and addition to implement this efficiently.

---

# Background Subtraction Algorithm

Each live RGB444 pixel is separated into:

```text
Rlive
Glive
Blive
```

The corresponding background pixel is separated into:

```text
Rbackground
Gbackground
Bbackground
```

---

## Luminance Calculation

A grayscale-like luminance value is calculated as:

```text
Y = (R + 2G + B) / 4
```

This does not convert the displayed image to grayscale.

The image remains RGB.

The luminance is only used internally for foreground detection.

---

## Difference Calculation

The FPGA calculates:

```text
dy = |Ylive - Ybackground|

dr = |Rlive - Rbackground|

dg = |Glive - Gbackground|

db = |Blive - Bbackground|
```

Then:

```text
max_rgb = max(dr, dg, db)
```

---

# Foreground Score

The foreground score is:

```text
foreground_score = 2 × dy + max_rgb
```

This gives more importance to luminance change while still considering color change.

---

# Threshold

The pixel is classified as foreground when:

```text
foreground_score > threshold
```

The final default threshold is:

```text
3
```

when:

```text
SW8:SW3 = 000000
```

If `SW8:SW3` is non-zero, the switch value becomes the threshold.

### Threshold Effect

Lower threshold:

```text
More sensitive
More foreground detected
More possible noise
```

Higher threshold:

```text
Less sensitive
Cleaner background
Possible loss of foreground regions
```

---

# Raw Foreground Mask

After thresholding:

```text
1 = foreground
0 = background
```

This produces a 1-bit binary mask called:

```text
foreground_raw
```

---

# 3×3 Majority Filter

The raw foreground mask may contain isolated noisy pixels.

The `mask_filter_3x3.v` module examines a 3×3 neighborhood:

```text
P1 P2 P3
P4 P5 P6
P7 P8 P9
```

The number of foreground pixels is counted.

The final implementation uses:

```text
4-out-of-9 majority rule
```

If at least four pixels are foreground:

```text
output = foreground
```

otherwise:

```text
output = background
```

The final code uses:

```verilog
out_mask <= (ones >= 4'd4);
```

This removes isolated noise while preserving foreground regions better than a stricter 5-out-of-9 rule.

---

# Mask Buffer

The filtered mask is stored in `mask_buffer.v`.

Each location requires only:

```text
1 bit
```

because:

```text
0 = background
1 = foreground
```

Mask resolution:

```text
320 × 240
```

# RGB Output Module

The internal pixel format is RGB444:

```text
12 bits
```

The DE2-115 VGA interface uses:

```text
8 bits Red
8 bits Green
8 bits Blue
```

The `RGB.v` module expands each 4-bit color channel by repeating the nibble.

Example:

```text
4'b1010
```

becomes:

```text
8'b10101010
```

During VGA blanking:

```text
R = 0
G = 0
B = 0
```

# `sig_activity.v`

Camera timing signals change too quickly to observe directly on LEDs.

The `sig_activity` module:

1. Synchronizes the asynchronous signal
2. Detects a transition
3. Loads a hold counter
4. Keeps the LED ON for approximately 0.17 seconds

This allows fast camera signals to be visually checked.

|---|---:|---|
| `CAM_D` | 8 bits | OV7670 parallel data bus |

# How to Run

1. Connect the OV7670 camera to JP5 using the pin mapping above.
2. Connect the DE2-115 board to a VGA monitor.
3. Open the Quartus project.
4. Select the device:

```text
EP4CE115F29C7
```

5. Compile the project.
6. Program the DE2-115 FPGA.
7. Set:

```text
SW9 = 0
SW8:SW3 = 000000
SW2 = 0
SW1 = 0
SW0 = 0
```

8. Verify that the normal camera image is visible.
9. Keep the camera stationary.
10. Ensure no foreground object/person is present.
11. Wait a few seconds for camera exposure to stabilize.
12. Press `KEY1` once.
13. Verify that `LEDG1` indicates a valid background.
14. Enter the camera view.
15. Set:

```text
SW0 = 1
```

16. The unchanged background should become black.
17. Foreground objects should remain visible.
18. Set:

```text
SW1 = 1
```

to display the binary white foreground mask.

# Limitations

The current system uses a fixed reference background.

Therefore:

- The camera must remain stationary after background capture.
- Large lighting changes may create false foreground detections.
- Shadows may be classified as foreground.
- Moved background objects may appear as foreground.
- Camera auto-exposure or white-balance changes may introduce noise.
- The system detects changed regions and does not specifically identify humans.
